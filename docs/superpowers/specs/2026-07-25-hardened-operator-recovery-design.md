# Hardened Operator Recovery Design

**Status:** Approved code-only production-readiness milestone  
**Date:** 2026-07-25

## Goal

Replace Sentinel's programmatic-only recovery hooks with a narrow, authenticated operator workflow for two already documented incidents:

1. requeue one exact quarantined source transaction; and
2. confirm one exact destination transaction whose original submission outcome was ambiguous.

Recovery must restore evidence-backed progress without creating a second authority path. It cannot submit a new cross-chain verification, change a GenLayer decision, extend a signer authorization, mark an unproven transaction successful, or expose a browser mutation.

This milestone creates no deployment, transaction, signer key, cloud resource, public endpoint, or funding requirement.

## Alternatives

### Selected: state-bound 3-of-5 recovery council

Five recovery identities, separate from the five DVN signer identities, authorize a short-lived EIP-712 proposal. Exactly three unique approvals are required. The proposal is derived from current durable state, waits through a configured timelock, and is applied only after the state and chain evidence are independently reverified.

This adds independent authorization without pretending that several processes controlled by one operator are decentralized. Operational independence still requires five distinct custody and failure domains.

### Rejected: local OS-user authorization

Filesystem permissions and an interactive confirmation are useful defense in depth but leave one host identity with unilateral recovery power. They are insufficient as the authorization model.

### Deferred: on-chain recovery governor

An on-chain timelock/governor would improve public auditability and custody separation, but it requires contracts, deployment, gas, governance accounts, and external review. Those actions remain blocked until explicit user approval.

## Trust boundary

Recovery authorization and DVN signing are separate roles. The private runtime manifest contains exactly five sorted, nonzero recovery operator addresses and a fixed quorum of three. None may equal a configured DVN signer address. The code proves address uniqueness and role separation; operational review must prove distinct people, accounts, devices, networks, and custody providers.

The CLI never accepts a mnemonic, private key, raw signer provider, browser wallet session, or environment-variable secret. Operators sign the prepared typed proposal outside Sentinel with hardware-wallet, HSM, KMS, or reviewed account tooling. Sentinel receives only public addresses and detached signatures.

The dashboard remains read-only. There is no HTTP recovery endpoint, form, reset button, or unauthenticated mutation.

## Configuration

The private runtime manifest adds:

```json
{
  "recovery": {
    "operators": [
      "0x1111111111111111111111111111111111111111",
      "0x2222222222222222222222222222222222222222",
      "0x3333333333333333333333333333333333333333",
      "0x4444444444444444444444444444444444444444",
      "0x5555555555555555555555555555555555555555"
    ],
    "quorum": 3,
    "minimumDelaySeconds": 900,
    "maximumLifetimeSeconds": 86400
  }
}
```

`minimumDelaySeconds` cannot be less than 900. `maximumLifetimeSeconds` cannot exceed 86400 or be shorter than the minimum delay plus 300 seconds. These are security floors and ceilings, not silently tunable demo defaults.

The deployment digest is the ABI-encoded hash of the source and destination chain IDs, EIDs, Endpoint, SendUln302, source OApp, destination OApp, Sentinel DVN/adapter, receive library, and GenLayer policy contract. A proposal for another Sentinel deployment cannot be replayed.

## Proposal format

`sentinel recovery prepare` emits one exact `RecoveryProposalV1` JSON document. JSON key order is not trusted; strict parsing rejects missing and unknown keys before reconstructing the typed values.

Common fields:

- `version`: exact integer `1`;
- `kind`: `INGESTION_REQUEUE` or `DESTINATION_CONFIRM`;
- `deploymentDigest`: exact runtime deployment binding;
- `subject`: source transaction hash for ingestion or packet GUID for destination;
- `expectedState`: `DEAD` or `RECOVERY_REQUIRED`;
- `expectedFailureCode`: the current allowlisted durable failure code;
- `preconditionDigest`: hash of the complete recovery-relevant durable record;
- `candidateTransactionHash`: zero bytes32 for ingestion or the discovered destination transaction hash;
- `nonce`: externally unpredictable, nonzero bytes32 generated by `prepare`;
- `preparedAt`, `executeAfter`, and `expiresAt`: UNIX seconds represented as canonical decimal strings.

The EIP-712 domain is:

- name: `GenLayer Sentinel Recovery`;
- version: `1`;
- chain ID: configured destination chain ID;
- verifying contract: configured Sentinel destination adapter;
- salt: `deploymentDigest`.

The typed `RecoveryProposal` contains every common field. Action-specific values that are not meaningful use a fixed zero value rather than an omitted field, producing one unambiguous signing schema.

`executeAfter - preparedAt` must meet the configured minimum delay. `expiresAt - preparedAt` cannot exceed the configured maximum lifetime, and at least 300 seconds must remain after `executeAfter`. Application requires `now >= executeAfter` and `now < expiresAt`.

## Approval validation

`sentinel recovery apply` accepts the private runtime manifest and one bundle containing the unchanged proposal plus exactly three approvals sorted by recovered lowercase address.

For every approval Sentinel:

1. validates the canonical signature shape;
2. recovers the EIP-712 signer;
3. requires the recovered signer to equal the declared address;
4. requires membership in the five configured recovery operators;
5. rejects duplicates, unsorted identities, unknown fields, and extra signatures.

The proposal digest is the durable recovery action ID. A previously applied action returns its existing sanitized receipt without repeating any mutation. A conflicting action cannot satisfy the original precondition digest.

## Runtime exclusion

The coordinator owns a durable runtime lease in the shared SQLite database. The lease records a random process identity, acquisition time, heartbeat time, and `ACTIVE` or `RELEASED` state.

The runtime:

1. binds its loopback status listener before claiming a stale lease;
2. refuses startup if another process still owns the listener or has a live lease;
3. renews the heartbeat around every scheduled tick;
4. records `RELEASED` only after scheduling is stopped, the active tick drains, HTTP closes, and all mutation-producing work has ended.

Recovery `prepare` is read-only and may observe an active runtime, because the resulting precondition must still survive the timelock and application checks. Recovery `apply` requires a cleanly `RELEASED` lease. A stale heartbeat is never enough for the CLI to take ownership. After a process crash, operators must restart the coordinator under its normal loopback ownership, let it reclaim the stale runtime lease, and stop it cleanly before applying recovery. This favors integrity over emergency availability; Sentinel is intended to remain an optional DVN.

The CLI acquires an exclusive recovery lease for the duration of application. Concurrent attempts either return the already-applied receipt for the same action ID or fail with the stable, deliberately nonspecific `RECOVERY_RUNTIME_ACTIVE` lease code.

## Ingestion recovery

`prepare ingestion-requeue <transaction-hash>`:

1. loads the exact `DEAD` recovery record and retained `DetectedPacket`;
2. validates its pathway, transaction hash, block number/hash, allowlisted failure code, and serialized packet invariants;
3. decodes the canonical LayerZero packet;
4. reruns two-provider source receipt and historical source-path verification;
5. binds the packet digest, source configuration digest, dead-letter metadata, and retained packet hash into `preconditionDigest`;
6. emits the unsigned proposal without changing state.

`apply` repeats every durable and chain check. After authorization and timelock validation:

1. it idempotently restores the retained packet to the listener inbox;
2. in the recovery database transaction, it resolves the dead letter and appends the applied audit receipt.

The ordering remains crash safe. If the process stops after inbox restoration but before resolution, repeating the same signed action observes the idempotently restored packet, completes resolution, and records one applied receipt.

Requeue does not claim that the packet is authorized. Normal ingestion must fetch current authoritative governance evidence, reconstruct the policy request, repeat deterministic verification, obtain finalized GenLayer consensus, and collect a fresh eligible signer quorum.

## Destination recovery

`prepare destination-confirm <guid> <candidate-transaction-hash>`:

1. loads the exact outbox record;
2. requires `RECOVERY_REQUIRED` with `SUBMISSION_AMBIGUOUS` or `USED_WITHOUT_RECEIPT`;
3. binds the complete signing envelope, execution digest, original failure code, and candidate transaction hash into `preconditionDigest`;
4. reruns destination pathway verification;
5. asks both configured destination RPC providers to prove the candidate receipt, exact `Verified` event bindings, adapter `used(executionDigest)`, shared block hash, and minimum confirmation depth;
6. emits nothing unless the result is fully `CONFIRMED`.

`apply` repeats the state, path, receipt, event, used-state, and confirmation checks after the timelock. Only then may a dedicated outbox recovery method atomically:

- transition the unchanged record directly from `RECOVERY_REQUIRED` to `CONFIRMED`;
- attach the independently proven transaction hash and confirmation count; and
- append the applied audit receipt.

The action never transitions to `READY`, `ATTEMPTING`, or `SUBMITTED`, and it never calls the destination submitter. The normal runtime may later advance the already-confirmed GUID to OApp execution after its ordinary coordinator invariants pass.

Wrong, reverted, unavailable, disputed, under-confirmed, event-mismatched, or adapter-unused candidates leave the outbox unchanged.

## Audit ledger

Applied actions are appended to a dedicated SQLite recovery-audit table containing:

- action ID and proposal kind;
- deployment, subject, precondition, and candidate-transaction digests;
- the three recovered operator addresses;
- prepared, executable, expiry, and applied timestamps;
- stable result code;
- previous receipt hash and current receipt hash.

The receipt hash commits to the complete sanitized row and prior receipt hash, producing a local tamper-evident chain. It does not make a database administrator unable to rewrite the whole database. The CLI prints the current receipt hash so operators can archive or anchor it outside Sentinel. No signature bytes, raw RPC responses, credentials, packet payload, evidence body, or database path appear in dashboard or CLI output.

`GET /api/recovery-actions` exposes only sanitized applied receipts. The dashboard labels this evidence `OPERATOR RECOVERY`, displays the 3-of-5 approval count and action/result, and never offers a mutation.

## CLI surface

The only commands are:

```text
npm run recovery:prepare -- ingestion --manifest <absolute-runtime-manifest> --transaction <transaction-hash>
npm run recovery:prepare -- destination --manifest <absolute-runtime-manifest> --guid <guid> --transaction <candidate-transaction-hash>
npm run recovery:apply -- --manifest <absolute-runtime-manifest> --bundle <absolute-signed-bundle>
```

Paths must be explicit absolute arguments. Recovery does not read environment-variable fallbacks. Output is canonical JSON suitable for review and archival. Errors are allowlisted codes on stderr with a nonzero exit status; raw exceptions and upstream messages are suppressed.

## Failure handling

Proof, authorization, state-binding and lease-acquisition failures are fail-closed and leave the protected dead letter or outbox row unchanged. The implemented public service/CLI codes are:

- `RECOVERY_CLI_USAGE`
- `RECOVERY_CLI_INPUT`
- `RECOVERY_CLI_FAILED`
- `RECOVERY_INVALID_BUNDLE`
- `RECOVERY_NOT_FOUND`
- `RECOVERY_STATE_CHANGED`
- `RECOVERY_RUNTIME_ACTIVE`
- `RECOVERY_SOURCE_PROOF_FAILED`
- `RECOVERY_DESTINATION_PATH_FAILED`
- `RECOVERY_DESTINATION_PENDING`
- `RECOVERY_DESTINATION_FAILED`
- `RECOVERY_APPLY_FAILED`

`RECOVERY_RUNTIME_ACTIVE` also covers an unavailable recovery lease without disclosing internal lease state. A failure while resolving ingestion may leave only the idempotent inbox copy restored while the dead letter remains. A failure releasing resources after the protected transaction commits may be reported as `RECOVERY_APPLY_FAILED`; replay the exact same bundle to retrieve the already-written receipt before investigating. Neither condition authorizes a second destination broadcast.

An audit-chain mismatch blocks all new recovery. Operators must restore or investigate the database; the CLI cannot reset the chain.

## Testing

Automated coverage must prove:

- exact five-operator/three-signature configuration and separation from DVN signers;
- deterministic deployment and proposal digests;
- EIP-712 recovery through three real ephemeral wallets;
- rejection of two signatures, duplicates, unsorted approvals, wrong domain, wrong deployment, altered fields, expired/not-yet-executable proposals, and unknown JSON keys;
- runtime lease acquisition, heartbeat, clean release, stale observation, active-runtime refusal, and concurrent recovery exclusion;
- proposal invalidation when any protected durable field changes during the timelock;
- repeated two-provider source receipt and historical-path proof before ingestion requeue;
- crash-safe idempotent inbox restoration and exactly one audit receipt;
- repeated destination path/receipt/event/used-state/confirmation proof;
- no destination submitter call under every recovery path;
- atomic direct `RECOVERY_REQUIRED -> CONFIRMED` transition only for a proven candidate;
- replay returning the original receipt without mutation;
- audit-chain tamper detection;
- sanitized CLI, status API, and dashboard output;
- end-to-end local recovery from an induced ambiguous destination result through confirmed adapter state and later OApp execution;
- the complete existing unit, integration, contract, security, and wallet-originated E2E suite remaining green.

Tests use local EDR, injected transports, temporary SQLite databases, and ephemeral recovery wallets. They are not evidence of five independent operators, HSM custody, public RPC independence, or live testnet recovery.

## Threats addressed

- One or two compromised recovery identities cannot act.
- DVN signer compromise does not grant recovery authority.
- A valid proposal cannot be replayed across deployments or after its state changes.
- A stolen old proposal expires and cannot bypass the timelock.
- An operator cannot attach an unproven destination transaction or trigger a rebroadcast.
- Recovery cannot silently run beside an active coordinator.
- Partial crash recovery is idempotent and auditable.
- Dashboard compromise cannot mutate recovery state.

## Residual risks and non-goals

Three compromised recovery operators can authorize only the two narrow actions; independent chain and state checks still constrain them. A compromised host or database administrator can deny service and may rewrite all local data, including the audit chain. Two RPC providers can collude. SQLite remains single-host storage. Clock integrity, hardware custody, operator independence, external receipt anchoring, alert delivery, and ceremony procedures require deployment controls and drills.

This milestone does not implement an on-chain governor, key custody, hardware-wallet UI, certificate lifecycle, cloud infrastructure, destination rebroadcast, signer reauthorization, GenLayer decision override, OApp rollback, public recovery service, or mainnet support.
