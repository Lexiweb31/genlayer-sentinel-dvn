# Coordinator operations

## Keyless public pathway observation

The read-only pathway auditor is a separate operator command from the coordinator runtime and local wallet harness. It has no wallet, signing, submission, deployment, funding, GenLayer account, cloud, database, or publication capability. Its only network surface is four manifest-supplied credential-free HTTPS RPC transports and seven fixed read methods. Exact manifest preparation, provider review, deployment evidence, artifact schema, and exit codes are in [`PATHWAY_AUDITOR.md`](PATHWAY_AUDITOR.md).

Select two endpoints per chain only after proving that they are public, credential-free, support EIP-1898 block-hash reads, and are controlled by reviewed different operator families. Four different origins are required, but URL/domain/IP diversity is not operator independence. Update `config/rpc-provider-audit.json` only through a reviewed evidence commit; each row must bind the manifest label, origin digest, operator family, evidence digest, and evidence sources. The current registry contains no reviewed providers, so current live readiness remains blocked.

No public manifest was supplied for this milestone. Live smoke: **NOT RUN — PUBLIC RPC INPUTS NOT SUPPLIED**. Do not substitute test fixtures or discover endpoints from environment variables.

When explicitly authorized, generate one immutable artifact to a fresh absolute path:

```bash
npm run audit:pathway -- --manifest /absolute/path/to/public-pathway-observation.json --output /absolute/path/to/new-pathway-evidence.json
```

After the npm wrapper's build succeeds and the pathway CLI starts, exit `0` is an internally consistent read-only observation, not authorization; exit `2` is a usable blocked evidence record; and exit `1` is an untrustworthy/unsafe CLI execution failure whose stable allowlisted stderr code should be used. A pre-CLI build/npm failure may emit ordinary diagnostics and non-CLI exit behavior and produces no pathway artifact. Null deployment is the correct predeployment input and must remain blocked. Never edit, overwrite, or merge artifacts.

For monitoring, create a new artifact on each approved observation window and compare the exact raw file hash, `repositoryBindingSha256`, provider identities and independence state, pinned block number/hash, official and deployed code hashes, creation evidence, `configurationSha256`, decoded libraries/peers/Executor/confirmations/DVNs/threshold/adapters/signers, status, and complete blocker list. Block-number movement is normal; a changed hash at the same block, changed repository binding, code/configuration drift, operator-evidence expiry, or removed blocker without authoritative evidence is an integrity alert. Pause any separately deployed signer intake and investigate; the auditor itself controls no signer.

The dashboard accepts one operator-selected local canonical artifact, validates it in browser memory, and stores/uploads nothing. It does not fetch an evidence path or combine the artifact with operational lifecycle state. The static web package is locally buildable with `npm run build:site` and verifiable with `npm run test:site`; it is currently not published and has no live URL.

Rollback is Git revert of the reviewed policy/documentation change and rejection/deletion of generated local artifacts. The command makes no chain write, so there is no chain rollback. An artifact optionally bound into `readiness:bundle` cannot set `livePathwayValidated` or clear any human approval gate.

## Local wallet demo

`npm run demo:local -- --owner 0x...` is a separate loopback-only harness, not the production composition root. It validates the public owner before creating infrastructure, starts one isolated EDR chain and same-origin app on `127.0.0.1`, explicitly funds that address with local currency, deploys and configures the fixture contracts, transfers source OApp ownership, and creates four coordinator stores plus a durable local-executor attempt store in one temporary SQLite database. Shutdown cancels scheduling, drains active work, closes HTTP and stores in reverse order, destroys the provider/server, and removes only that session directory.

The harness exposes a sanitized `/api/demo/config` capability only after every local dependency exists. It rejects an owner address belonging to any unlocked EDR account before funding, deployment, or ownership transfer, preserving the boundary that only the injected wallet can originate the source action. The browser can encode only `record(bytes32)` for the fixed source OApp, destination EID, authorization ID, target, zero action value, empty options, and native fee shape. The wallet performs `eth_sendTransaction`; Sentinel never requests account signing methods or accepts a signing secret. Account, chain, or input changes invalidate an in-flight quote without accepting its stale result. Once wallet confirmation can produce a transaction, the page locks that harness session to one source action.

One tick mines a local confirmation block, ingests paired `PacketSent`/`DVNFeePaid` evidence, polls the pending/final fixture, plans eligible signing, and processes destination delivery serially. The coordinator/store restart method closes and recreates the dashboard and all store connections against the same EDR and database, exercising post-mining recovery without wallet resend.

Local proof and finality labels are mandatory:

- `LOCAL_EDR_FIXTURE_PACKET` and `LOCAL_EDR_FIXTURE_RECEIPT` are separate canonical/receipt checks against one EDR, not independent RPC origins.
- `LOCAL_POLICY_FIXTURE` compares exact authoritative evidence and action semantics but is not GenLayer consensus.
- Five EDR signers produce real ECDSA shares, but they are not five independent operators or failure domains.
- The local executor sends a real `MockEndpointV2.deliver` transaction, but it is not LayerZero infrastructure.

If the wallet returns a transaction hash and the receipt cannot be established, do not click-send repeatedly or alter state. Reconcile the local transaction hash first. `LocalOAppExecutionConfirmer` likewise reserves the GUID in the harness's SQLite attempt store before broadcast and refuses an automatic retry after an ambiguous result, including after its store connection reopens. It persists `LOCAL_EXECUTION_RECOVERY_REQUIRED`, exposes that code separately from the already-confirmed adapter transaction, and clears it only after the exact executed GUID and target mutation are observed. There is no unauthenticated browser clear action. The production destination outbox retains its stronger `ATTEMPTING`/`RECOVERY_REQUIRED` reconciliation model and independently confirmed adapter state.

## Startup preflight

Copy `config/sentinel-runtime.example.json` outside the repository, replace every `.invalid` origin and placeholder address from a fresh audited deployment manifest, and set filesystem permissions so only the coordinator identity can read it. Do not source environment variables from another product. `npm run preflight -- /absolute/path/to/private/sentinel-runtime.json` requires prototype mode; two distinct public HTTPS RPC origins on each side; nonzero Endpoint, library, OApp and adapter addresses; decimal block settings; an exact evidence host; a public HTTPS GenLayer endpoint; one absolute SQLite path shared by the transactional stores, runtime fence and audit ledger; positive poll and maximum-ingestion-attempt values; and loopback-only status binding. Source policy additionally requires matching padded/unpadded OApp identity, an explicit executor and maximum message size, complete sorted required/optional DVN arrays, Sentinel optional but never required, at least one independent required DVN, no Dead DVN, and a valid optional threshold. Destination policy requires an explicit non-default receive library, complete required/optional DVN arrays, Sentinel optional but never required, at least one independent required DVN, exactly five sorted DVN signer identities, quorum three, an explicit signature TTL and exact source/destination peer binding. Recovery policy separately requires exactly five sorted nonzero operator identities, quorum three, no overlap with the DVN signers, at least a 900-second delay, and a lifetime no longer than 86,400 seconds with at least 300 seconds to apply after the timelock. Its output strips RPC paths and hides the database path. Example confirmation, attempt and TTL values are explicitly test values.

Passing preflight does not authorize deployment or establish that addresses, libraries, DVNs, RPCs or GenLayer are current. Chain-state validation and explicit user approval remain separate gates.

## Runtime lifecycle

`composeRuntime` constructs one testnet-prototype process from a parsed manifest and injected capabilities: an account-aware `GenLayerContractClient`, exactly five signer services, a destination submitter, source and destination RPC access, and an explicit `LOCAL_TEST` or `EXTERNAL_INJECTED` presentation mode. It opens the listener, job, recovery and delivery-outbox SQLite stores plus the runtime/recovery lease; restores jobs plus policy and signing bindings; reconciles durable quorum; binds the same-origin dashboard; then claims one UUID-owned runtime lease before scheduling a serialized loop. Each tick heartbeats before and after acknowledged ingestion, all `POLICY_PENDING` polling, newly finalized `ALLOW` planning/signing, and destination delivery. A failure is reported and retried on the next interval without overlapping ticks; individual destination records are isolated so one bad delivery does not stall others.

The same coordinator process maintains a closed-schema, read-only runtime observation. It reports process lifecycle (`STARTING`, `RUNNING`, `STOPPING`, or `OWNERSHIP_LOST`), lease relationship, current phase, the last completed tick's bounded outcome and sanitized timestamps. This is useful operator evidence, but it is not an external process monitor, high-availability coordinator, or recovery gate:

| Observation | Operator interpretation |
| --- | --- |
| `RUNNING` / `CLAIMED` | Observe normal production-composition work; investigate stale phase or tick age independently. |
| `RUNNING` / `NOT_APPLICABLE_LOCAL_FIXTURE` | Local harness only; no production runtime lease is claimed. |
| `DEGRADED` tick outcome | Investigate the allowlisted failure code and deterministic records; do not initiate recovery from this signal alone. |
| `OWNERSHIP_LOST` / `LOST` | Normal work has failed closed. Stop the process and verify lease and chain state offline. |
| Endpoint unavailable | Establish process state and lease release independently; unavailability is not permission to recover. |

The coordinator constructs a read-only status client from the manifest's GenLayer HTTPS endpoint and polls `gen_getTransactionStatus` directly. It requires the exact `FINALIZED`/`7` pair before separately checking `FINISHED_WITH_RETURN` and reading the GUID-keyed policy record with the `latest-final` state variant. All other documented statuses remain pending; malformed or contradictory RPC responses fail closed. Submission, execution lookup and finalized contract reads still use the injected account-aware adapter, which has not been approved or exercised against a live GenLayer network.

Shutdown cancels future ticks, waits for an active tick, closes HTTP, cleanly releases the runtime lease, then closes all stores once in reverse acquisition order. A construction or startup failure closes every resource already acquired before rethrowing. Another active owner makes startup fail closed after HTTP is closed. Normal composition never requests stale takeover; `assertReleased` and recovery acquisition do not treat an old heartbeat as a clean release. The composition root rejects a signer set that does not exactly match the manifest and does not construct credentials itself. A standalone process entrypoint is withheld until the GenLayer direct-mode/account-provider contract, destination account provider and secure signer transport are approved; do not add a raw private-key environment variable as a shortcut.

The independent source and destination verifiers repeat critical checks even when a manifest already passed preflight: at least two distinct HTTPS origins, no credentials/custom ports/local or literal-IP targets, nonzero target addresses and positive confirmation depths. Injected transports are mandatory composition capabilities so account-provider policy can remain outside repository configuration. Distinct origins are not proof of independent operators; procurement and infrastructure review must establish separate providers and failure domains.

## Ingestion

`PacketFeeListener` polls finalized source blocks through `JsonRpcLogSource`. It filters the configured EndpointV2 and SendUln302 addresses for the official `PacketSent(bytes,bytes,address)` and `DVNFeePaid(address[],address[],uint256[])` topics. A detection is emitted only when both events occur in the same transaction. This proves a fee event exists but does not replace the later two-provider receipt and canonical packet verification.

The listener holds a block-number/hash cursor and rewinds by the configured lookback if the cursor block is no longer canonical. Events above `latest - confirmations` are not emitted. `SqliteListenerStore` checkpoints the cursor and seen transaction/block pairs under an explicit pathway key using WAL, full synchronous writes and an immediate transaction. A restarted listener resumes at the next block and retains deduplication state; reorg removal and the resulting new cursor are saved together.

New detections and the advanced cursor are checkpointed in one transaction before `poll()` returns. Pending packets are redelivered without scanning forward until the caller explicitly acknowledges their transaction hash. `IngestionRunner` invokes the handler first and acknowledges only after it resolves, so a failed job write remains retryable after restart. The durable coordinator then deduplicates retries by packet GUID.

`PolicyRequestFactory` is the only supported listener-to-policy assembly path. It requires the configured send library, exact source/destination EIDs and OApp peers, a positive Sentinel fee in the optional DVN list, and rejects Sentinel if configured as required. It decodes only the `TreasuryPolicyOApp.Action` tuple and renders a stable action record. `HttpsEvidenceSource` requires a non-empty exact-host allowlist; rejects HTTP, credentials, custom ports, localhost, literal IPs, redirects and unexpected content types; and applies a ten-second timeout. The factory rejects empty or oversized evidence before hashing the exact UTF-8 bytes with SHA-256.

Before the assembled request can reach GenLayer, `SourceBoundPacketVerifier` combines canonical packet/receipt verification with `IndependentSourcePathVerifier`. Both source providers must agree on chain ID and the packet's exact historical block hash. At that block each provider must report code at Endpoint, SendUln302, source OApp, executor, Sentinel and every configured DVN; an explicit non-default send library; supported destination EID; raw app ULN confirmations/DVN arrays/threshold; raw executor and message-size config; and the exact destination peer. The observations must agree with each other and the manifest. A shared nonzero configuration digest is attached to both deterministic receipt records, persisted in the job snapshot and shown as `source config` in the dashboard. Any failure prevents GenLayer submission. These are deterministic checks, not semantic consensus. The ingestion runner acknowledges only after request assembly, the combined proof and durable coordinator detection succeed.

Application URL validation does not prevent an allowlisted DNS name from resolving to a private address. Production deployment must pin the governance origin operationally, resolve through controlled DNS, deny private/link-local/metadata ranges at the network layer, restrict outbound destinations, and alert on certificate or address changes.

This is recoverable at-least-once delivery, not distributed exactly-once semantics. A handler must durably create or recognize the job before returning. Failed ingestion is recorded in `SqliteRecoveryStore` before any quarantine acknowledgement. At the configured limit the record becomes `DEAD`, allowing later packets to progress. Raw errors and payloads are not exposed by HTTP. Runtime recovery is now read-only: requeue is possible only through the detached operator-recovery workflow below. Apply reconstructs the canonical packet, repeats the combined receipt and exact historical source-path proof, compares every retained dead-letter field through an ABI-encoded precondition digest, requeues idempotently, then deletes the dead letter and appends its audit receipt atomically. Production still needs backoff policy, alert integration and pruning of acknowledged `seen` entries below a proven reorg horizon.

## Job recovery

`SqliteJobStore` uses WAL mode, full synchronous writes, explicit immediate transactions and schema versioning. Packet snapshots retain bigint fields without lossy number conversion. The coordinator persists `POLICY_PENDING` before the GenLayer submission, then persists its transaction hash. On restart, known GUIDs return the original request ID and are not resubmitted.

If submission may have reached GenLayer but its hash was not stored, the pre-submit intent remains without a request ID. The coordinator stops with `policy submission recovery required` instead of guessing or creating a second consensus request. An operator must reconcile GenLayer/account history and repair the record through a future audited recovery tool. Corrupt snapshots, unknown schema versions and GUID mismatches fail startup.

SQLite is appropriate for a single testnet coordinator, not active-active high availability. A production candidate needs one elected writer or a transactional shared database with fencing, backups, restore drills, encryption at rest and retention policy.

## Destination verification outbox

`SqliteVerificationOutbox` stores the exact canonical ULN302 verification intent in `SIGNING` before any signer call. The signed envelope binds chain ID, adapter, receive-library target, packet GUID/header/payload hash, exact `verify(bytes,bytes32,uint64)` calldata, confirmations, packet/evidence digests and expiry. The finalized `ALLOW`, policy record and policy version are checked before signing but are not separate execution-digest fields. The full ULN/DVN configuration is independently matched before planning and again before submission, but its diagnostic observation digest and five-member signer set are not fields in the signed envelope. The outbox itself is constructed with those five manifest identities and validates exactly three sorted, authorized signatures by cryptographic recovery before persisting `READY`. It advances the coordinator only after that write, and the worker requires the coordinator's exact durable signer list before broadcast. Expiry is checked after signer latency and again before submission; it never silently extends.

Before signing, `DestinationPathVerifier` requires both destination RPC providers to agree on chain ID, a shared minimum block height and that height's block hash. At that block it confirms bytecode at Endpoint, configured receive library and adapter; Endpoint `getReceiveLibrary` for the pinned OApp; receive-library `isSupportedEid`; both the merged effective ULN configuration and the raw app ULN configuration; and adapter target, 3-of-5 quorum plus all five authorized signers. Raw required/optional DVN values and threshold must explicitly match the manifest, so an inherited default is rejected even when the merged view looks correct. After every observed field matches, it computes a diagnostic digest over the authoritative view. The worker repeats verification immediately before submission and refuses to broadcast if the path drifted. Reads occur against one agreed block number/hash but are separate RPC calls, not an atomic state proof; a live integration must quantify and monitor this race.

`DestinationWorker` first revalidates the pathway and checks adapter usage, then persists `ATTEMPTING` before calling the injected account-backed submitter. A returned transaction hash advances to `SUBMITTED`. A submission exception is treated as ambiguous because the transaction may already have reached the network; the record moves to `RECOVERY_REQUIRED` and is never automatically rebroadcast.

`IndependentDestinationVerifier` requires at least two distinct public HTTPS RPC origins. Both must agree on a successful receipt, block number/hash, the configured adapter's exact `Verified` event bindings, minimum confirmation depth and `used(executionDigest) == true`. Insufficient confirmation depth remains pending. A confirmed adapter transaction atomically sets used state and calls its verification target, so the coordinator persists `EXECUTED` only after this evidence. Failed, disagreeing, wrong-event, unused or unavailable observations use allowlisted failure codes rather than raw provider messages.

For `RECOVERY_REQUIRED`, pause automated delivery and reconcile the destination account nonce/history plus both RPC providers. Do not edit SQLite or blindly resubmit. The detached recovery CLI can confirm a discovered hash only after the council, timelock, released-runtime fence, current outbox binding, repeated destination pathway proof, two-provider receipt/block/event/used-state proof, and configured confirmations all pass. It never owns a submitter and cannot broadcast. The composed runtime ticks the ordinary worker only through injected capabilities; the repository deliberately ships no account provider, raw key loader, credentialed signer implementation or standalone production entrypoint.

The Endpoint, SendUln302, start block, confirmation depth and RPC URL must come from an audited deployment manifest. They must never silently default. RPC credentials belong in the coordinator secret store, not the dashboard or repository.

## Detached operator recovery

Recovery operators are a separate five-member council from the five DVN signers. The prototype threshold is exactly three. Three operators can authorize a recovery proposal, but they cannot bypass the deterministic source or destination verifiers, change the proposal after signing, use a proposal for another deployment, shorten the minimum delay, extend the expiry, resubmit an ambiguous destination transaction, or mutate through HTTP.

1. Stop the coordinator through its normal lifecycle and retain evidence that HTTP closed and the runtime lease was cleanly released. Do not kill the process mid-tick and assume a stale heartbeat is sufficient.
2. Reconcile the incident. For ingestion, identify the exact quarantined source transaction. For destination, obtain the already-mined candidate transaction hash from account history and both configured RPC operators.
3. Prepare without mutation:

   ```bash
   npm run recovery:prepare -- ingestion --manifest /absolute/runtime.json --transaction 0xSOURCE_TX_HASH
   npm run recovery:prepare -- destination --manifest /absolute/runtime.json --guid 0xGUID --transaction 0xDESTINATION_TX_HASH
   ```

4. Distribute the unchanged proposal plus the reviewed public recovery domain to five independent operators. Each operator must independently reconstruct `recoveryTypedData`, confirm the deployment digest, action kind, subject, expected state/failure, precondition digest, candidate hash, nonce, `executeAfter`, and `expiresAt`, then sign through its own offline or HSM-controlled EIP-712 workflow. This repository intentionally does not accept a key, mnemonic, wallet callback or signer provider for the ceremony.
5. Assemble exactly three sorted detached approvals into `{"proposal":...,"approvals":[...]}`. Preserve the original proposal bytes. Wait until `executeAfter`; do not wait until or beyond `expiresAt`.
6. Apply while the coordinator remains stopped:

   ```bash
   npm run recovery:apply -- --manifest /absolute/runtime.json --bundle /absolute/detached-bundle.json
   ```

7. Independently archive the proposal, operator identities, approval evidence, receipt and current hash-chain head. The database stores only the three operator addresses and receipt fields, not signatures. Exporting the chain head is essential: an administrator with unrestricted database access can otherwise truncate and recompute local history.
8. Restart the coordinator normally. Confirm that the lease is claimed once, the requeued source packet returns to ordinary deterministic/policy processing, or the confirmed destination record advances through ordinary OApp execution without another adapter submission.

The proposal lifetime may be at most one day and the application window after the timelock must be at least five minutes. `apply` validates signatures and time before acquiring recovery ownership. It returns an existing identical receipt before acquiring the lease on replay. Ingestion writes the packet back to the durable inbox before atomically resolving the dead letter; a crash between those operations leaves an idempotent pending packet and an unresolved incident, so repeating the same authorized action is safe. Destination confirmation and its receipt are one transaction. Any state, packet, envelope, share, digest, failure-code, timestamp, pathway, receipt, event, used-state or confirmation drift fails closed with an allowlisted recovery code and no protected mutation.

There is no on-chain recovery governor, live HSM integration, independent-operator attestation service, public proof endpoint, deployed recovery council or mainnet claim. Changing council membership changes the off-chain authorization policy, but a partial membership change does not itself change the deployment digest. Rotate all five identities or change the deployment domain when immediate cryptographic invalidation of every outstanding proposal is required; otherwise stop preparation, reject old bundles operationally, distribute the reviewed manifest through a controlled ceremony, and wait through the bounded one-day maximum lifetime before resuming.

## Status API and capability-gated app

`createStatusServer` exposes `GET /health`, including the explicit presentation mode, `GET /api/runtime-status`, `GET /api/jobs`, `GET /api/jobs/:guid`, sanitized `GET /api/dead-letters`, sanitized `GET /api/deliveries`, sanitized `GET /api/recovery-actions`, and capability-gated `GET /api/demo/config`. Other methods are rejected. Runtime status uses exact lifecycle and lease values, returns a sanitized `503` if its live reader is unavailable or invalid, and never exposes the lease owner or a raw exception. It is the serving process's observation only and never establishes permission to run recovery. The recovery endpoint exposes action/subject/candidate hashes, three operator addresses, timing, result and receipt-chain hashes; it omits signatures, deployment/precondition digests, packet/evidence content, RPC paths and database location. The capability endpoint returns `404` unless the explicit local harness injects a strict immutable configuration. Responses disable caching, safely encode bigint fields as decimal strings, and contain no key material, signatures, call data, encoded quarantined payload, RPC paths with credentials, database path, or raw exception. The server does not create jobs, requeue packets, apply recovery, submit transactions, or sign messages.

`createDashboardServer` serves that API, eight reviewed dashboard assets, and exactly one generated self-contained wallet bundle at `/assets/demo.js`. It rejects other generated/dist paths and methods and applies no-store, nosniff, no-referrer, restrictive Permissions-Policy and a self-only Content-Security-Policy with framing, base and form actions disabled. The dashboard contains no external font, script, CDN, inline script, or dynamic import.

The operations workspace fetches `/health`, `/api/runtime-status`, `/api/jobs`, `/api/dead-letters`, `/api/deliveries`, and `/api/recovery-actions` from the same origin every five seconds. It labels the runtime `LOCAL TEST`, `EXTERNAL INJECTED` or unavailable; shows the coordinator process observation with a permanent warning that it is not failover, high availability, or recovery authorization; selects an observed wallet GUID only after that GUID exists in real coordinator state; and keeps deterministic proofs, semantic result, signer quorum, sanitized quarantine incidents, delivery state and recovery receipts separate. The recovery section has no button, form, signing action or mutation request. The action workspace is disabled in ordinary local and `EXTERNAL_INJECTED` composition. When enabled by the local harness, it sends directly through the injected provider to the source OApp; it never POSTs to the coordinator and cannot request signer shares, destination submission, recovery, deployment, or funding. If an API is absent, invalid, or empty, the app explicitly displays unavailable/empty state and never substitutes a job or receipt.

## Alerts

Alert on reorg rewinds, unpaired packet/fee events, RPC errors, cursor lag, repeated GUIDs, long-lived lifecycle stages, expired `SIGNING`, GenLayer undetermined/failure states, destination-path drift, signer divergence, quorum latency, destination persistence failure, runtime `DEGRADED`, `STOPPING`, or `OWNERSHIP_LOST`, runtime-lease conflicts, stale heartbeats, any recovery proposal/application error, audit-chain verification failure, unarchived receipt-chain heads, `RECOVERY_REQUIRED` and rejected OApp execution. Logs must use redacted RPC origins and GUID/transaction identifiers, never URLs containing credentials or signature/key material.
