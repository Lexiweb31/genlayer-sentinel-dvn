# Threat model and trust assumptions

Protected assets are DVN signing authority, recovery authority, policy integrity, packet/evidence bindings, wallet intent, destination execution, audit history, and operator truthfulness. Attackers may control one RPC, coordinator instances, dashboard inputs, evidence hosting, TLS endpoints, fewer than either threshold, or privileged SQLite access; reorder/replay requests; duplicate one signer/operator identity behind several endpoints; induce reorgs; exploit semantic ambiguity; inject a malicious wallet/provider; switch accounts or chains after quoting; replace or revert a source transaction; spoof a GUID in browser state; race runtime shutdown and recovery; truncate or recompute a local audit chain; misrepresent fixtures as decentralized consensus; or expose a loopback service beyond its intended host.

Controls: two-provider agreement plus confirmation depth; canonical hash recomputation; exact historical packet-block agreement; explicit source send library, raw ULN, executor, peer and bytecode checks; persisted nonzero source-configuration digest; rejection of destination ULN values inherited from defaults; immutable per-GUID request binding; strict ABI/allowlist checks before semantic review; evidence content digest and freshness window; finalized (not merely accepted) GenLayer state; domain-separated DVN signing payload with chain, adapter, GUID, decision and expiry; canonical versioned signer requests; mutual-TLS/SPKI identity pinning at the deployment boundary; durable request replay and conflicting-GUID rejection before signing; unique authorized signer-address recovery and on-chain used-digest tracking; idempotent state transitions; key isolation behind signer-provider interfaces; independent required/optional LayerZero DVNs. Recovery adds a separate five-operator council and exact three-signature EIP-712 quorum; deployment-domain salt; kind/state/failure/candidate/precondition binding; a minimum 15-minute delay and bounded lifetime; a durable runtime/recovery mutex that requires explicit release; repeated deterministic source or destination proof; no destination submitter dependency; protected state change plus hash-chained receipt in one SQLite transaction; replay-stable receipts; sanitized error codes; and a read-only API/dashboard.

Local app controls: the demo capability is absent by default and accepted only for loopback HTTP, chain `31337`, one source OApp, one destination EID, one target, `record(bytes32)`, zero action value, empty options, native fee payment, and an explicitly labeled semantic fixture. The browser serializes wallet connection, rechecks chain ID and the OApp’s on-chain owner before quote and send, invalidates an in-flight quote on account/chain/input change without accepting a stale result, calls `eth_sendTransaction` exactly once, preserves an in-flight or submitted transaction boundary, accepts exactly one bound `ActionSent` event from the configured OApp receipt, and never infers policy or execution from mining. A terminal harness session cannot originate a second fixed-authorization action. Only `/api/jobs/:guid` and `/api/deliveries` can produce policy rejection, delivery incident, or execution presentation. The operations workspace does not create a placeholder job for a browser GUID.

The local harness binds both EDR and app to `127.0.0.1`, validates the public owner before startup, rejects that owner if it matches any unlocked harness account, uses an OS-selected EDR port, funds only that supplied address explicitly, keeps ephemeral signer capabilities in process memory, and prints no signer material or database path. Static governance evidence and semantic finality are labeled `LOCAL_POLICY_FIXTURE`; local packet proofs include `LOCAL_EDR_FIXTURE`; external injected mode remains read-only. Browser reload restores no approval state. A post-mining coordinator/store restart rediscovers the original transaction without asking the wallet to send again. A separate durable local-executor store records an ambiguous OApp-delivery incident across reopen and removes it only after exact on-chain execution evidence is observed. The operator-recovery E2E uses five additional ephemeral wallets distinct from the five DVN signer accounts; it proves cryptographic 3-of-5 approval and one real local adapter/OApp recovery path, not independent operators or deployed custody.

Residual risks: GenLayer validator/model correlation, governance source compromise, both source or destination RPCs lying consistently, non-atomic multi-call state reads at one block, destination chain/account/nonce failure, signer or recovery-operator implementation compromise, certificate-authority compromise, stale/unrotated pins, multiple nominal operators under common control, three colluding recovery operators, LayerZero or adapter bugs, finality/API interpretation errors, reservation-triggered denial of service, ambiguous transaction broadcast, fee volatility, malicious browser extensions, local-machine compromise, and general signer/operator unavailability. Recovery can restore progress but cannot reverse an executed action, prove operator independence, or repair a destination transaction that never reached the chain. A local receipt hash chain is tamper-evident only relative to a previously exported trusted head; unrestricted database administrators can truncate or recompute uncheckpointed history. There is no on-chain recovery governor, HSM enforcement or independently witnessed ceremony. A wallet can lie about displayed calldata; users must verify the configured local OApp and action in their wallet. Loopback is not an authentication boundary on a compromised host. The current page does not restore a submitted hash/GUID after reload; the coordinator still retains the real state, but the user must select the observed GUID. Source receipt ambiguity and destination intent-before-broadcast prevent unsafe automatic replay but can require manual reconciliation. A semantic `ALLOW` is not proof of source-chain inclusion. A deterministic pass is not governance authorization. A historical configuration digest proves agreement over decoded observations, not the independence or honesty of the two providers. Fixture proof labels are not independent infrastructure, and injected transport tests are not evidence that production custody, mutual TLS, HSM controls or independent failure domains exist.

Rollback: stop the local harness to destroy its isolated chain and remove its temporary database; for a deployed system, pause job intake and signer issuance, complete a clean runtime lease release, preserve and externally checkpoint the audit head, remove Sentinel from optional DVNs using OApp owner governance, and rotate DVN signers through an audited adapter migration. Rotate recovery membership through a reviewed manifest ceremony. Because partial council rotation does not change the deployment digest, immediate invalidation of every outstanding proposal requires rotating all five identities or changing a deployment-bound identity; otherwise keep recovery paused until the bounded one-day maximum proposal lifetime has elapsed. Never reuse an old signed bundle after deployment or council changes. Never rewrite finalized decisions; deploy a new policy version and explicitly migrate only future GUIDs. Already executed cross-chain actions are not reversible by Sentinel.
